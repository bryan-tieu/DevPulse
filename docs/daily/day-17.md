> **Phase 3 · Week 6 (🏁 the last item).** Picks up from Day 16 (three sessions, 2026-07-21 → 08-05): `dashboard/` renders four Streamlit panels over the API and never touches BigQuery — honest empty/NULL/unknown states, `Unknown` at **178,081/180,386 (98.7%)** shown and captioned, split-TTL caching (marts 300 s, `/runs` 30 s), host suite **93** green in **0.43 s**. Every gate this project owns — `dbt build`, the GE validation, `ruff`, `black`, `pytest` — is a gate Bryan remembers to run. Today the repo starts checking itself: a push, a machine that has never seen this code, and a red X when something is wrong.
>
> **Scope call (read first):** IN — `.github/workflows/ci.yml` with three independent jobs (**lint** · **test** · **dbt-parse**), the env-var wiring that makes an import-time-strict `config.py` survive a machine with no `.env`, exact `==` pins on the three host requirements files, a committed CI dbt profile, required status checks on `main`, and one real PR that the checks actually gate. OUT — **anything needing GCP credentials**: `dbt build` against BigQuery, GE's `validate_silver` (it reads GCS), the Spark tests (no PySpark on the runner), any deploy stage, Dependabot + a hash-pinned lockfile (named, deferred), and Workload Identity Federation (designed in `decisions.md`, **not built** — it is a day of its own). No `terraform apply`, no rehydrate, **no cloud spend at all** — the first day of this project with none.
>
> **The day's central decision, stated up front and honestly:** *what is CI allowed to need?* Today: **nothing but the repo** — no credential, no cloud, no data. A hermetic pipeline that runs on a stranger's machine in 90 seconds and costs $0. **Rejected (and when each wins):** *an SA key in GitHub Secrets* — the answer in most tutorials, and **banned by hard rule #4**: a long-lived key sitting in a third party's secret store, printable by any workflow anyone adds later, is exactly the credential this project has refused to mint since Day 2. It genuinely wins only on CI systems with **no OIDC support** (older self-hosted Jenkins), and even there the key should be short-lived and scoped to a throwaway project. *Workload Identity Federation* (GitHub's OIDC token exchanged for a short-lived GCP token) is **the correct keyless answer** and wins the moment CI must truly touch the cloud — integration tests against a sandbox dataset, `terraform plan` on a PR, a deploy. It costs a Terraform pool + provider + SA binding, and it carries a classic footgun: an `attribute_condition` that forgets to pin the repository lets **any** GitHub repo assume your service account. Deferred deliberately, designed in writing. *Running `dbt build` + GE in CI against real data* wins when the warehouse has a cheap CI sandbox and the team's dominant failure mode is SQL that only breaks against real rows; it costs money on every push and makes CI flaky on cloud availability. *No CI, rely on local discipline* wins for a genuinely throwaway solo repo — and loses here for a specific reason worth saying out loud: **every host command in this project has only ever run on Windows 10 / PowerShell, while every container it ships is `python:3.11-slim` (Linux).** Today is the first Linux execution of the host code path in 128 commits. Budget for it going red. The production-vs-simplified line: **hermetic CI proves the code is well-formed, not that the pipeline produced the right numbers.** Nothing today validates that silver is 180,386. Single runner, single Python version, no matrix, no Docker layer cache, no deploy, and branch protection an owner can override — *exercised, not stress-tested*, and the sentence that separates it from a real CI estate is "no job here has ever touched real data."

## Environment notes (Windows 10 · PowerShell · Docker Desktop)
**Nothing to rehydrate and nothing to provision.** No `terraform apply`, no `/start-session` chain, no Airflow, no `uvicorn`, no Streamlit. Docker Desktop is needed only for step 4's local iteration (`docker build` on `dbt/`). Today's instrument is the **GitHub Actions tab in the browser** — the same role the uvicorn access log played on Days 15–16: the ground truth of what actually ran.
- **Remote confirmed:** `origin` → `https://github.com/bryan-tieu/DevPulse.git`, default branch `main`, **no `.github/` directory yet**. Confirm in step 0 whether the repo is **public** (Actions minutes free) or **private** (2,000 free minutes/month) — it changes nothing you build, but you should know which bill you're on, and on a public repo **workflow logs are world-readable**, which is why step 2 forbids `printenv`-style debugging.
- **`gh` CLI is not installed.** Everything today is doable from the browser (Actions tab, Settings → Branches, the PR page). `winget install GitHub.cli` is optional convenience, not a prerequisite — don't spend the day yak-shaving a CLI.
- **The iteration loop is push-driven, and that is the day's friction.** A YAML typo is only discoverable after a commit + push, and the honest failure mode is a branch littered with `fix ci`, `fix ci again`, `fix ci for real`. Two mitigations, both real: (1) work on a branch (`ci/day-17`) so `main` stays clean and step 5 has something to gate; (2) **run every command locally, in the exact form the workflow will use, before you commit it** — `ruff check .`, `black --check .`, `python -m pytest tests/ -q`, `docker build -t devpulse-dbt dbt/`. That is run-as-you-write applied to YAML, and it is the single highest-value habit on this day.
- **Auth posture is unchanged and, for once, irrelevant** — CI holds no credential of any kind. Keyless ADC still governs every local path. 🔐 The pre-deploy gate (auth · rate limiting) is untouched today; dependency pinning gets **partially** closed in step 3.
- **The one CI idea people get wrong:** a workflow that runs on `push` to `main` is a **notification** — the broken code is already the trunk when the email arrives. A **required status check on a pull request** is a **gate** — the merge button is disabled until it's green. Same YAML, completely different guarantee, and the difference is configured in repository Settings, not in the workflow file. Step 5 is where the day pays off.

## Focus
Build `.github/workflows/ci.yml` with three jobs that run on every push and every PR: **lint** (`ruff check .` + `black --check .`), **test** (`pytest tests/` → **93 passed**, with the four `config.py` env vars supplied as *obviously fake* job-level values), and **dbt-parse** (build the pinned `devpulse-dbt` image, then `dbt deps` + `dbt parse` against a committed credential-free CI profile — catching a broken `ref()` without a warehouse or a dollar). Pin `requirements.txt`, `requirements-dev.txt`, and `dashboard/requirements.txt` to exact versions so that "green yesterday" means something today. Then turn the workflow from a notification into a gate: required status checks on `main`, one real PR from `ci/day-17`, checks blocking the merge, and each gate **proven red at least once on purpose** before it's trusted. End state: a green badge on the README, Phase 3 closed, and a clear written boundary between what CI proves (the code is well-formed) and what only a real run proves (the numbers are right).

0. **Baseline green + the branch, and *not* rehydrating on purpose.** 🤖 Deliberate non-actions first: **no `terraform apply`, no ingest, no Spark, no dbt build** — CI's entire premise is that it needs none of it, and standing up infra you won't read from is pure cost. Confirm locally: `git remote -v` (origin present), `python -m pytest tests/ -q` → **93 passed**, `ruff check . && black --check .` clean, `docker ps` empty. In the browser: repo **visibility** (public/private) and that the **Actions tab exists and is enabled** (a fork or a disabled-Actions repo will silently never run a workflow — check before you debug YAML that was never executed). Then `git switch -c ci/day-17` — today ends in a PR, and CI fixes pushed straight to `main` would defeat step 5 before it starts. *(Setup, not a commit.)*

1. **The lint job — the smallest workflow that can fail correctly.** 🧑‍💻 New `.github/workflows/ci.yml`: a `name`, the triggers, three top-level keys worth understanding, and one `lint` job — `runs-on: ubuntu-latest`, `actions/checkout@v4`, `actions/setup-python@v5` with `python-version: "3.11"`, `pip install -r requirements-dev.txt`, then `ruff check .` and `black --check .` as separate steps.
   The teaching, four parts. (a) **Pin the Python version to what you ship**, not `latest`: every image in this repo is `python:3.11-slim` and `pyproject.toml` says `target-version = "py311"` — CI running 3.13 would test a version that never runs anywhere. (b) **`black --check`, never `black`** — CI reports, it does not rewrite. A workflow that formats and commits is a workflow that pushes code nobody reviewed, and it needs write permissions to do it, which brings us to (c) **`permissions: contents: read`** at the top: the `GITHUB_TOKEN` is injected into every job, and stating least privilege explicitly means a future step that tries to push fails loudly instead of succeeding quietly. (d) **`concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }`** — three pushes in five minutes shouldn't leave three runs racing; only the newest answer matters. Also decide, out loud: `actions/checkout@v4` is a **mutable tag** — the supply-chain-hard form is a full commit SHA (`@8f4b7f8…`), because a compromised or retagged action runs arbitrary code with your token. SHA + Dependabot is the rigorous answer; tags are readable. Pick one, comment *why*.
   Gotchas: YAML errors surface only after a push, and GitHub's editor-side validation is weak. `on:` is a real YAML pitfall (in YAML 1.1 the bare word `on` parses as boolean `true` — GitHub handles its own file, but this is why quoting keys is a habit worth having). Note that `on: [push, pull_request]` makes a PR from a **same-repo branch run every job twice** (once per event) — halve it with `push: { branches: [main] }` + `pull_request:`, and say why that's the shape you want.
   **Verify:** commit, push the branch, watch the run appear in the Actions tab and go green. Then **prove it can fail**: add an unused import to any module, push, watch `ruff` turn the check red, revert. *A green check you have never seen fail is not a gate* — the Day-12/13 rule, applied to CI. *Commit: `add github actions lint job`.*

2. **The test job — and the env vars that are config, not secrets.** 🧑‍💻 Add a **second job** (`test`), not another step in `lint`: separate jobs run in parallel and report independently, so you learn that lint *and* tests failed, not just whichever came first. `pip install -r requirements.txt -r requirements-dev.txt` (both — `tests/conftest.py` imports `api.cache` at module scope, so runtime deps are not optional), then `python -m pytest tests/ -q`.
   **The blocker to expect, and it will not look like a test failure:** `config.py` calls `_require()` at **import time**, so on a machine with no `.env` the run dies during *collection* with `RuntimeError: Missing required env var GCP_PROJECT` — zero tests run, and the traceback points at config, not at CI. The fix is a job-level `env:` block supplying `GCP_PROJECT`, `BRONZE_BUCKET`, `BQ_DATASET`, `BQ_GOLD_DATASET`. The teaching, three parts: (a) **config is not a secret.** The project id and bucket names are in `CLAUDE.md`, in Terraform, and in a hundred commits — their disclosure harms nothing. Secrets are for values where *disclosure itself* is the damage. Stuffing non-secrets into GitHub Secrets makes the workflow unreadable, unauditable by a reviewer, and *harder* to debug (secrets are masked in logs, so your echo prints `***`). (b) **Make the values obviously fake** — `ci-project`, `ci-bronze-bucket`, `ci_silver`, `ci_gold`. This is a blast-radius control: if a test ever accidentally reaches the network, it fails against a project that does not exist instead of quietly reading or writing real infrastructure. (c) Predict before you push: does anything break under fake values? `tests/test_queries.py` imports `GCP_PROJECT`/`BQ_GOLD_DATASET` and builds its expectations *from* them, so it should pass with any string — **and if some test does fail, that test is coupled to production config, and finding it is worth more than the green check.**
   Note the honest gaps while you're here: PySpark isn't installed on the runner, so `conftest.py`'s `collect_ignore` skips `test_silver_events.py` exactly as it does on your laptop — CI collects **93**, and the Spark tests therefore have **no CI home at all** (their home would be the Spark image, deferred). And say the interview line about *why* a 93-test suite runs in **0.43 s with zero credentials**: the pure-transform/IO split, `dependency_overrides`, the fake transport, the injected clock. Hermetic CI is not something you configure at the end — it is something the code architecture either permits or forbids, and this one permits it.
   🔏 **Never `printenv`, never `cat .env`, never echo a variable to debug** — on a public repo those logs are world-readable and permanent.
   **Verify:** the Actions log shows `93 passed`; the job is green. Once, deliberately, delete one env var from the block and watch the import-time explosion so you recognise it instantly the next time. *Commit: `add github actions test job`.*

3. **Pin the dependencies — CI is what turns "unpinned" from a smell into a bug.** 🧑‍💻 Rewrite the three host requirements files with exact `==` pins (from the current working set): `requirements.txt` → `requests==2.34.2`, `google-cloud-storage==3.12.0`, `google-cloud-bigquery==3.42.1`, `fastapi==0.138.1`, `uvicorn[standard]==0.49.0`, `python-dotenv==1.2.2`; `requirements-dev.txt` → `ruff==0.15.20`, `black==26.5.1`, `pytest==9.1.1`, `httpx2==2.5.0`; `dashboard/requirements.txt` → `streamlit==1.60.0`, `requests==2.34.2`.
   The teaching: on a laptop, unpinned deps drift **slowly and invisibly** — your venv was resolved months ago and nothing re-resolves it. **CI installs from scratch on every single run**, which converts that latent drift into a build that was green yesterday and red today from a release you didn't make, with a `git diff` that shows nothing. Two supporting points: (a) **this project already knew the answer** — `quality/requirements.txt` is pinned with a comment saying precisely this ("reproducible builds, no surprise minor bumps"), and `dbt/Dockerfile` pins `dbt-bigquery==1.11.3` + `sqlfluff==3.4.2`; the **host** files were the exception, and CI is what exposed it. Note the ceiling comment on `pandas==2.3.3` in `quality/` as the model for *why* a pin gets written down. (b) Now add `cache: pip` to `actions/setup-python` — and understand the coupling: the cache key is a **hash of the requirements files**, so caching an *unpinned* file is actively wrong (same key, different resolved content). Pinning is what makes the cache honest, which is why these two land in the same commit.
   **The gap to state, not fix:** direct pins are not a lockfile — every **transitive** dependency still floats (`google-cloud-bigquery` pulls a dozen). The complete fix is `pip-tools`/`uv` compiling a fully-pinned, **hash-verified** lockfile (`--require-hashes`) plus Dependabot to age the pins deliberately. Update the `decisions.md` backlog line to "direct deps pinned ✅; lockfile + hashes + Dependabot open" rather than closing it.
   **Verify:** `pip install -r requirements.txt -r requirements-dev.txt` still resolves locally (no conflict introduced by pinning two files that share `requests`); local suite still **93**; CI green; on the **second** CI run the setup-python log shows a **cache hit** and a visibly faster install. *Commit: `pin python dependencies`.*

4. **The dbt gate CI can actually run — `parse`, not `build`.** 🧑‍💻 A third job (`dbt-parse`): `docker build -t devpulse-dbt dbt/`, then run `dbt deps` and `dbt parse` in that image against a committed CI profile.
   Why this exact shape, four reasons. (a) **`dbt build` needs a warehouse and money; `dbt parse` needs neither** — and parse still catches a broken `ref()`, a model renamed without its `.yml`, a YAML syntax error, a missing package, a duplicated model name. That is the large majority of what actually breaks in a dbt PR. The residue it *cannot* catch — SQL that compiles but returns wrong rows, a failing `not_null` test — is exactly the residue that needs real data, which is the WIF day you deferred. Name the split explicitly; it is the whole point of the day in miniature. (b) **Use the image, never the compose file.** `dbt/docker-compose.yaml` bind-mounts `${APPDATA}/gcloud/application_default_credentials.json` and reads `../.env` — both are **facts about your Windows laptop** that do not exist on a Linux runner, and per hard rule #8 a missing bind source becomes a *silent empty directory*, so compose would fail confusingly rather than cleanly. Compose encodes a developer's machine; CI wants the artifact. (c) Building the image in CI also proves **the Dockerfile still builds** — image rot caught for free, and it's the same pinned image the Airflow DockerOperator runs. (d) `dbt/profiles.yml` is **gitignored**, so add `dbt/profiles.ci.yml` (`method: oauth`, `project: ci-project`, `dataset: ci_gold`, `threads: 1`) and point dbt at it with `DBT_PROFILES_DIR` / `--profiles-dir`. It contains **no credential** — which is exactly why it is safe to commit, and worth a comment saying so. Note the symmetry with step 3: `package-lock.yml` is already committed, so `dbt deps` is reproducible for the same reason pinned requirements are.
   **Gotcha to expect — this is the step's real debugging.** `dbt parse` should not open a warehouse connection, but adapter initialization can still attempt to resolve credentials depending on version. If it does: **read the error before reaching for a fix**, and say what you observe. Honest fallbacks in order — set a dummy `GOOGLE_APPLICATION_CREDENTIALS`-free environment and retry; if parse genuinely insists on a connection, keep `dbt deps` + `dbt_project.yml`/YAML validation in CI, leave `parse` local, and **log it as a finding** rather than papering over it. Same treatment for `sqlfluff lint models` under the dbt templater (the templater resolves `ref()` by running dbt's own machinery, so it inherits whatever parse needs): try it, and if it needs a live connection it stays a local gate — written down, not pretended.
   **Verify:** job green in Actions. Then **prove it red on purpose**: change a `ref('stg_events')` to `ref('stg_event')` in one mart, push, watch the parse fail with a compilation error naming the missing node, revert. *Commit: `add dbt parse gate to ci`.*

5. **Turn a notification into a gate — one real PR.** 🧑‍💻 Repository **Settings → Branches** (or Rules → Rulesets): protect `main`, require a pull request, and require the status checks `lint`, `test`, `dbt-parse` to pass. Then open the PR from `ci/day-17`, watch three checks attach to it, push one deliberate lint break to the branch and see the **merge button disable**, fix it, merge when green. Write that sentence down; it's the anti-cargo-cult answer to "we have CI, so we're covered."

## Constraints & conventions
- 🧱 **One lesson: CI proves what can be proven without credentials — and the hermetic/credentialed boundary is a design decision, not an accident.** WIF, deploys, image publishing, Dependabot, matrix builds → named, deferred.
- 🚫 **No service-account key in GitHub Secrets, ever** — not even "just to see `dbt build` go green once" (hard rule #4; a key in a third-party store is the exact thing this project has refused to create since Day 2). **No `dbt build`, no GE run, no Spark job, no `terraform apply` in CI today.** **No auto-formatting or auto-committing workflow.** **No new pipeline, model, or API code** — if a CI failure tempts a source change, stop and write it up: a Windows-ism that only Linux catches is the most interesting finding available today, not a detour.
- 🔗 **Tests:** the suite stays **hermetic — 93 collected, zero credentials, zero network**. Any test that would need a credential to pass in CI is a *design* bug in that test, not a CI configuration problem; fix the seam, don't add a secret. Spark tests skip in CI exactly as on the host — an honest, named gap.
- 🔏 **PII / secrets hygiene:** no `printenv`, no `cat .env`, no echoing variables to debug — on a public repo workflow logs are world-readable and permanent. `dbt/profiles.ci.yml` is committable **only because it contains no credential**; say so in a comment so nobody later "helpfully" adds one.
- 💸 **Cost: $0 cloud.** Nothing provisioned, no BigQuery job of any kind, no bytes scanned. Actions minutes are free on public repos (2,000/month private); `concurrency` + `cancel-in-progress` and the pip cache keep the burn small either way. The Docker build in step 4 is the longest job — accept it, or note layer-caching as a future optimisation you chose not to build.
- 📐 **Lint:** `ruff` + `black` clean repo-wide; YAML at 2-space indent; **every non-obvious workflow key carries a `#` comment saying why** — `permissions`, `concurrency`, the pinned `3.11`, `--check`, the fake env values, the action-pinning choice. A workflow nobody can explain is a workflow nobody will fix.
- 📦 **Five commits, imperative mood:** `add github actions lint job` · `add github actions test job` · `pin python dependencies` · `add dbt parse gate to ci` · `require ci checks and add status badge` · plus the docs commit.
- 🔐 **Backlog carried:** dependency pinning **partially closed** (direct pins ✅; lockfile + hashes + Dependabot open). API auth + rate limiting remain the pre-deploy gate — CI green is not a security control. Pipeline-SA impersonation + the silver-bucket grant are still pending, and note the connection: **WIF is the same keyless idea as SA impersonation**, so today's written design makes that item cheaper when it comes up.

## Learning goals
1. **Hermetic vs credentialed CI is the first design decision, not a detail** — a pipeline that needs no secret runs on any machine in seconds, costs nothing, and can never leak; the price is that it can only prove the code is *well-formed*. Knowing precisely which failures live on each side of that line (a broken `ref()` vs a failing `not_null` test) is what makes the split defensible instead of lazy.
2. **Why an SA key in CI is the wrong keyless-shaped answer, and what the right one is** — Workload Identity Federation exchanges a short-lived, repo-scoped OIDC token for a short-lived cloud token, so there is no long-lived credential to steal or rotate; and the classic misconfiguration (a trust condition that doesn't pin the repository, letting any GitHub repo assume the SA) is the detail that shows you've actually thought about it.
3. **Config is not a secret, and treating it as one makes things worse** — secrets are for values whose *disclosure* is the harm; putting a project id in a secret store makes the workflow unreviewable and its logs unreadable. The corollary is sharper: CI config should be **deliberately fake**, so an accidental network call fails loudly instead of touching production.
4. **Testability is an architectural property that CI simply reveals** — 93 tests in 0.43 s with no credentials is a dividend of the pure/IO split, `dependency_overrides`, the fake transport, and the injected clock. A suite that can't run hermetically doesn't have a CI problem; it has a coupling problem, and adding a secret to fix it hides the real defect.
5. **Unpinned dependencies are a latent bug that only a from-scratch install exposes** — a laptop resolves once and never again, so drift is invisible until CI reinstalls on every run. Direct `==` pins are the floor; a hash-verified lockfile plus a bot that ages pins deliberately is the ceiling, and knowing the gap between them (transitive deps still float) is the honest version of "we pin our dependencies."
6. **Compose files encode a developer's machine; CI wants the artifact** — bind-mounted ADC and a local `.env` are laptop facts, and a missing bind source silently becomes an empty directory. Building the same pinned image the orchestrator runs gives you Dockerfile-rot detection for free.
7. **A workflow is a notification; a required status check on a PR is a gate** — the same YAML, a completely different guarantee, and the difference is repository configuration. And the limits matter: an owner can override branch protection on a personal repo, and green means well-formed, not correct — no job in this pipeline has ever seen a row of data.
